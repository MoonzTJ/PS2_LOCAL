2. YOUR TEST A — TRACE THE UPDATE PATH, WITH THESE KNOWN ANCHORS

I agree with recovering the conditions on the actual movement/transform path.
We already have these matching-build anchors (all code addresses below are
RVAs relative to the matching image, preferred base 0x140000000):

  engine+B010 -> selected actor manager
  manager+2450 -> selected actor; manager+2458 -> matched identity
  actor+200 -> character GUID
  actor+918 -> transform object
  transform+130 -> vector named velocity by native diagnostics
  transform+180 bit 0 -> matrix cache dirty
  transform+1C0 -> clean matrix position row observed by the helper
  actor+1BA0 -> speed field used by ExpectedSpeed
  actor+268C -> separately named vertical velocity field

The position getter follows actor virtual+210 -> thunk13895 -> B92D60.
B92D60 uses actor+918 and calls 93ECD0 to obtain the matrix; 93ECD0 recomputes
a dirty derived matrix. Our read-only helper reads the position row only when
the dirty bit is clear, and performs stable rereads. It never calls the getter
or updates the game cache.

The verified UpdateLocation path is:
  A4B9B0 case 0x0C / A4C615
  -> actor virtual+820 / BDFAC0
  -> virtual+218 / BDF9B0 -> B9E2E0, plus BDDDE0 for facing
  -> raw/matrix transform setters 941690 / 941310

That is a location/transform application path. Neither it nor 93ECD0 alone
is established as the per-frame velocity integrator. The next trace should
connect the diagnostic velocity vector, underlying transform/physics state,
position setters and the scheduled local-player update, including who calls
it and whether it actually runs. The derived matrix cache may be downstream
of the relevant integration rather than the integration destination itself.

Existing format-13 ZIPs are bounded field reports, not full memory dumps.
Unobserved health/deployed/controller/physics fields cannot be read from those
old ZIPs. Once native accessors/layouts and candidate predicates are recovered,
a small versioned observer can capture the justified fields in a future test,
keeping exact type/GUID checks and the global read bound. No native game
calls, forced flags or arbitrary offset probing are needed.

A false field alone is not enough to identify the unique blocker: we need
to establish its meaning, that the relevant path is reached, which branch is
taken and whether multiple prerequisites are false. Likewise, satisfying one
deploy condition would not rule out other lifecycle/controller dependencies.

4. YOUR TEST C — USEFUL OBSERVATIONS, WITH NARROWER INTERPRETATION

Mouse-look, translation and menu/chat focus should be reported separately.
Rotation would show that some camera/input path works; it would not by itself
prove the camera is attached to the player actor. A bound camera can also be
locked or lose input. A fixed view alone does not prove absence of attachment.

A new packet prefix correlated with a deploy/map click is worth preserving,
but it is not automatically a decoded deployment request. It can include
time-varying fields or be a UI selection/query message. Our existing logger
keeps only four prefix bytes. A useful follow-up should retain direction,
channel, exact bounded payload and event timing, then trace the current native
producer/consumer. It should not infer an obligatory reply from silence alone.

Those are useful future discriminators after static tracing; this reply does
not ask Moon to rerun the same test or perform a broad collection immediately.
